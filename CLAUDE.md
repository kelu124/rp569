# rp569 — RP2350B × CH569 board (KiCad)

## Objective

Design, in KiCad, a board pairing a **Raspberry Pi RP2350B** (QFN-80, 48 GPIO) with a
**WCH CH569W** (RISC-V, USB 3.0 SuperSpeed, HSPI, eMMC/SD controller):

- **CH569** → USB 3.0 connector (USB-B SS or USB-C SS, TBD) + SD card on its eMMC/SDIO pins.
- **RP2350B** → USB 2.0 on a USB-C connector (device, firmware/debug/test-control).
- **Inter-chip links**: shared I2C, one UART, and an **8-bit** parallel bus + clock (+ handshake
  lines; 8-bit because 16-bit HSPI collides with the SD pins, see D-003) — RP2350B (PIO) produces high-speed data, CH569 receives it (HSPI) and exports it over USB 3.
- **Logic analyser**: 8 RP2350B GPIOs are sampled (logic levels) by PIO and streamed over the
  parallel bus to the CH569 → USB 3.
- **User I/O**: one RGB LED on each chip (RP2350B and CH569).
- **Breakout I2C buses** (separate from the shared inter-chip I2C): one on RP2350B for extra
  devices, one on CH569 GPIOs (bit-banged if no HW I2C). Headers with pull-ups.
- **Power**: USB-C and USB3 VBUS ORed by ideal diodes (no back-feed) for the RP2350 side; the CH569 is fed
  from its own USB3 VBUS through a load switch controlled by the RP2350 (see `docs/power.md`).
- **Test automation**: RP2350B controls CH569 RESET# and boot-mode strap so CH569 can be
  (re)flashed and power-cycled without human intervention.

## Hardware workflow

- **Source of truth: `hardware/gen/board.py`.** Edit it, then run `hardware/gen/build.sh` (regenerates
  schematic, PCB and net classes, then runs ERC, DRC and schematic parity into `hardware/reports/`).
- `gen_pcb.py` needs the system Python (`/usr/bin/python3`, it imports `pcbnew`).
- **Routed board: `hardware/rp569-routed.kicad_pcb` (v1.0, hand-finished)**; production files with
  `python3 hardware/gen/gen_fab.py` → `hardware/jlcpcb/` (DRC-gated gerbers zip, BOM, CPL). After a `board.py` change
  the routed board is stale: update it in pcbnew (*Update PCB from Schematic*) or re-route.
- Routing: `build.sh` produces an unrouted board. Two autorouting options, see `docs/layout.md` § Routing options:
  Freerouting via `hardware/gen/route.py` (patched 2.1.0 jar, on hold) and KiCadRoutingTools (`hardware/gen/route_krt.sh`, `~/tools/KiCadRoutingTools`,
  used for v1.0). Watch every routing run with 3-minute progress reports (skill `kicad-board`).
- `build.sh` / `gen_pcb.py` only rewrite the generated `hardware/rp569.kicad_pcb`; they never touch the hand-routed
  `rp569-routed.kicad_pcb`. Carry schematic changes into the routed board with pcbnew's *Update PCB from Schematic*.

## Working rules

- After finishing a task: move it from `.claude/todo.md` to `.claude/done.md` (with date).
- Versions (D-025): `firmware/*/version.yaml`, `python/rp569/_version.py`, major.minor.patch. The pre-commit hook bumps
  the patch of every touched component; **never change major/minor** (the user does). A firmware command change
  needs the matching `@command` method in `python/rp569/` or the commit is refused.
- Every commit: append an entry to `.claude/commits.md` (see `project-logs` skill).
  Write the entry as `pending` in the commit itself, then fill in the real hash in the next commit.
- Any non-obvious hardware choice (part, pin assignment, topology) goes in `specification.md` (§2), and any new requirement in §1.
- Pin assignments must be checked against the datasheets (CH569DS1, RP2350 datasheet) —
  never from memory. Note the datasheet section/table used.
- KiCad version: KiCad 8+ (TBD — confirm installed version). Keep custom symbols/footprints
  in a project-local library under `hardware/lib/`.
